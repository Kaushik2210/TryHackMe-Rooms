## Overview

A Security Operations Center (SOC) is the team and function responsible for continuously monitoring an
organization's networks, endpoints, and applications for signs of malicious activity, and for responding
when something is found. A Junior/Tier 1 SOC analyst is typically the first human in that pipeline: alerts
generated by automated tooling (SIEM correlation rules, EDR detections, IDS/IPS signatures) land in a
queue, and the analyst's job is to triage each one quickly and accurately — deciding what is noise, what
is a true positive, and what needs to be escalated. This guide describes that real-world workflow, the
tools it depends on, and the tiered structure most SOCs use to scale it.

## Core Concepts

### SOC tiering

Most SOCs are organized into tiers that separate triage speed from investigative depth:

- **Tier 1 (Triage Analyst).** Monitors the alert queue, performs initial classification (true
  positive / false positive / needs escalation), documents findings in the ticketing system, and
  escalates anything that meets escalation criteria. Tier 1 work is high-volume and follows documented
  playbooks/runbooks closely rather than improvising.
- **Tier 2 (Incident Responder).** Receives escalated alerts, performs deeper investigation across
  multiple log sources, determines scope and impact, and drives containment and eradication actions.
  Tier 2 analysts typically have deeper tooling access (memory/disk forensics, malware sandboxing) and
  more latitude to deviate from a playbook when the situation demands it.
- **Tier 3 (Threat Hunter / Subject Matter Expert).** Performs proactive hunting for threats that
  automated detection missed, tunes detection content (writing or refining SIEM correlation rules and
  EDR detections), and often leads major incident response and post-incident root-cause analysis.

This structure exists to route the highest volume of work (raw alerts) to the people who can process it
fastest, while reserving the scarcest and most senior skill (deep investigation, detection engineering)
for the alerts and threats that actually warrant it.

### The alert triage workflow

A typical Tier 1 triage pass on a single alert follows a repeatable structure:

1. **Read the alert context** — what rule or signature fired, what asset/user/IP it involves, and its
   assigned severity.
2. **Validate the alert** — pull the raw log(s) that generated it to confirm the alert accurately
   reflects what happened (detection logic can misfire; confirming against source data catches this).
3. **Gather supporting context** — check related logs from other sources (was this IP seen elsewhere?
   does this user normally log in from this location? is this process normally run on this host?),
   check threat intelligence feeds/reputation for any IOCs involved, and check asset criticality.
4. **Classify** — true positive (malicious and confirmed), false positive (benign, alert logic or data
   was misleading), or benign true positive / non-issue (accurately detected but not a security concern,
   e.g. authorized penetration testing traffic).
5. **Decide next action** — close with documented rationale, escalate to Tier 2 per the escalation
   criteria in the runbook, or take a pre-authorized containment action if the playbook permits it at
   Tier 1 (e.g., isolating a host via EDR).
6. **Document** — every alert gets a documented disposition in the ticketing/case-management system, both
   for audit purposes and so the next analyst (or the same analyst months later) has a paper trail.

Playbooks (also called runbooks) exist specifically so this process is consistent across analysts and
shifts — a well-run SOC does not rely on individual judgment alone for common alert types.

### Common log sources

A Tier 1 analyst typically pulls from several categories of data during triage:

- **SIEM (Security Information and Event Management)** — aggregates and correlates logs from across the
  environment (endpoints, network devices, applications, cloud services) into a searchable index and
  generates alerts from correlation rules. Common platforms include Splunk, Microsoft Sentinel, and
  Elastic Security.
- **EDR (Endpoint Detection and Response)** — agent-based telemetry from individual hosts: process
  creation, file writes, registry changes, network connections, and behavioral detections. EDR tooling
  (e.g., CrowdStrike Falcon, Microsoft Defender for Endpoint) is usually the richest source of
  host-level context during an investigation.
- **Firewall and network device logs** — connection/session logs, allowed/denied traffic, and
  increasingly, next-gen firewall application-layer visibility (DNS queries, URL categories, TLS SNI).
- **IDS/IPS (Intrusion Detection/Prevention System)** — signature- and anomaly-based network alerting,
  commonly Suricata- or Snort-rule-based, sitting inline or on a network tap/SPAN port.
- **Identity provider / authentication logs** — sign-in events, MFA challenges, and conditional access
  decisions from systems like Active Directory, Entra ID, or Okta, which are central to detecting
  credential-based attacks.
- **DNS and proxy logs** — frequently the fastest way to spot command-and-control beaconing or
  data exfiltration to a malicious domain.

### Frameworks that structure the work

Two reference frameworks show up constantly in real SOC work:

- **MITRE ATT&CK** — a knowledge base of adversary tactics and techniques observed in the real world,
  used to classify what stage of an attack a given alert represents (e.g., Initial Access, Persistence,
  Lateral Movement) and to identify detection coverage gaps.
- **The SANS/NIST incident handling lifecycle** — commonly summarized (per the SANS PICERL model) as
  **Preparation, Identification, Containment, Eradication, Recovery, and Lessons Learned**. Tier 1 triage
  work sits primarily in the Identification phase; escalation hands the incident to Tier 2/3 for
  Containment onward.

## Why It Matters for Security

The Tier 1 SOC role is the volume filter that makes the rest of an organization's security program
sustainable — without accurate, consistent triage, either real incidents get lost in alert noise or
analysts burn out chasing false positives. It is also the most common entry point into a security career:
the skills built here (log analysis, calm methodical investigation under alert pressure, clear
documentation, knowing when to escalate rather than guess) transfer directly into incident response,
threat hunting, detection engineering, and eventually security leadership roles. From an organizational
risk perspective, mean-time-to-detect and mean-time-to-respond — two of the most important security
metrics a SOC is measured on — are driven directly by how efficiently Tier 1 triage functions.

## Common Pitfalls / Misconfigurations

- **Alert fatigue from poorly tuned detections.** A high false-positive rate trains analysts to
  rubber-stamp alerts as benign, which is how genuine incidents get missed; detection tuning (Tier 3
  work) is what keeps Tier 1 triage trustworthy.
- **Closing an alert without pulling the underlying raw log.** Trusting only the alert summary can miss
  context that changes the classification entirely.
- **Skipping documentation on "obvious" false positives.** Undocumented dispositions make it impossible
  to spot a pattern later (e.g., the same "false positive" recurring because it is actually a
  low-and-slow attack).
- **Escalating everything, or escalating nothing.** Both defeat the purpose of tiering — the former
  overwhelms Tier 2/3, the latter risks a real incident staying with an analyst who lacks the access or
  authority to fully investigate it.
- **Treating playbooks as absolute rather than a baseline.** Runbooks cover the common case; an analyst
  who blindly follows a playbook step that clearly doesn't fit the situation in front of them can miss
  the actual threat.
- **Ignoring time zones and log clock skew** when correlating events across multiple log sources — a
  frequent, easy-to-miss source of investigative errors.
